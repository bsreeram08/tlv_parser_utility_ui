# Architecture

## Runtime shape

```text
Astro route + BaseLayout
        │
        ├── Bearnie styles and native Astro components
        │
        └── WorkspaceIsland (client-only React seam)
                 │
                 ├── workspace shell and pane lifecycle
                 ├── tool registry and calculator renderer
                 ├── payment-tool views
                 └── browser adapters: IndexedDB, clipboard, files

Framework-independent TypeScript
        ├── EMV / BER-TLV
        ├── ISO 8583 / APDU
        ├── cryptography / PIN blocks
        └── converters / validation
```

## Module decisions

### Astro host module

**Interface:** routes render layouts and may include native Bearnie modules or explicit client islands.

**Implementation:** `src/pages/`, `src/layouts/`, and `astro.config.mjs`.

Astro owns HTML, metadata, global styling, static builds, and future content-oriented routes. A route must not recreate browser workspace state.

### Bearnie design-system module

**Interface:** semantic tokens plus owned `.astro` modules under `src/components/bearnie/`.

**Implementation:** files generated by the Bearnie CLI and customized locally. `src/styles/bearnie.css` is imported before product-specific theme overrides in `src/index.css`.

Bearnie is the project-level design-system source. `bearnie.json` records its directories. There is no `components.json` and the shadcn CLI is no longer part of the repository.

### Workspace module

**Interface:** `WorkspaceIsland` mounts the complete local payment workspace with no server props.

**Implementation:** `src/App.tsx`, `src/components/workspace/`, the React tool views, and their internal UI adapters.

This is one deep client module because pane order, active focus, drag/reorder state, keyboard commands, archive state, theme state, and local persistence change together. Splitting each tool into a separate island would expose a larger coordination interface and scatter browser-state synchronization across callers.

The registry keeps tool metadata eager for search and navigation, but lazy-loads substantial tool views when their first pane opens. This preserves a single state seam without paying the download and parse cost for every tool at startup.

Tabs, collapse, zoom, and archive hide already-mounted panes instead of unmounting them, so in-progress values survive canvas layout changes. Restored workspace tabs that have not been visited remain unmounted until first activation, retaining lazy startup behavior.

The React modules under `src/components/ui/` are compatibility adapters, not a public design-system interface. They consume Bearnie semantic tokens while preserving the accessible Radix behavior needed by complex, already-shipping tool flows.

### Payment-domain modules

**Interface:** typed inputs produce typed results or readable validation errors.

**Implementation:** `src/utils/`, `src/tools/specs/`, and registry data.

Payment-domain logic must not import Astro, React, Bearnie, or DOM modules. Browser capabilities such as IndexedDB and clipboard access sit in adapters at the UI seam.

## Placement rules

- Add a static route, layout, fallback, or documentation surface with Astro and Bearnie.
- Add a calculator by declaring a specification in `src/tools/specs/`.
- Add a stateful payment tool through the tool registry and keep its computation in `src/utils/`.
- Do not create another client island unless it has independent state and can operate without workspace coordination.
- Do not import `.astro` modules into React. Astro may render React islands, but React imports only React/TypeScript modules.
- Do not restore Vite entry files, `components.json`, or a second package-manager lockfile.

## Security and verification

- Bun is the sole package manager and `bun.lock` is canonical.
- `bun run security:advisories` blocks `keyv@6.0.0` from GHSA-3p9h-f68w-m6fx.
- `bun run build` runs the advisory gate, Astro diagnostics, and the production static build.
- Browser QA must cover workspace restore, TLV parsing, copy behavior, multiple panes, keyboard navigation, tabs/zoom, themes, and reduced motion.

## Deployment

Astro emits the production site to `dist`. Firebase Hosting serves that directory directly through `firebase.json`; no framework backend or server runtime is required. The merge workflow builds with the repository's pinned Bun version before publishing to the live `payment-tlv-utilities` site.

## Migration direction

The framework and design-system ownership have moved to Astro and Bearnie. React remains only where continuous client state earns it. A React view should move to native Astro/Bearnie only when it becomes static or progressively enhanced and can cross the workspace seam without adding coordination complexity.
